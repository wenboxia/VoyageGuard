# VoyageGuard · 出行气象决策 Agent

把实时气象数据与官方发布的预警/禁航标准自动比对，告诉你**今天有没有越过某条官方的线**。
飞机与船只两种场景，中英双语。

**这个项目真正想证明的**，不是"我写了个 ReAct agent"，而是两件更难的事：

> 1. 在一个安全相关的 AI 产品里，哪些环节**必须是确定性的**，哪些才交给模型；
> 2. 我**查证了自己的知识库**——发现一半的阈值站不住，于是把它重建成只用官方数据，
>    并用**真实停航记录**反过来验证。

## 最重要的一条：我们能说什么，不能说什么

上一版的输出长这样：

> ❌ **高风险（停航预警）** —— 风速 12 m/s 超过近海游船 10.8 m/s 的安全停航红线

看起来很专业。但它有两个问题，而且第二个更严重：

1. 那个 10.8 确实有出处，但**"跨海客滚船 17.2"是编的，而且比真实标准（约 7 级 / 13.9）宽松**——
   一个安全产品犯了"该警告时不警告"这个方向的错。
2. **「停航预警」这句话我们没资格说。** 那是在预测某条船会不会停航。

交通运输部对人大建议的[答复函](https://xxgk.mot.gov.cn/jigou/haishi/202006/t20200630_3319352.html)
说得很清楚：船舶抗风能力按**风压**计算，与蒲福风级**不是对应关系**，所以官方
**故意不在船舶证书上标注抗风等级**，理由是"容易引起社会误解"。真实链条是：
每条船有自己的稳性限制 → 船公司判断 → 海事部门可下令 → 地方另有一刀切规定。

现在的输出：

> ✅ **高风险**
> · 〔法规〕烟台 — 海面风力已达 7 级（14.0 m/s）；按规定，海面风力 7 级以上不得允许旅客、车辆上船
>   〔[山东省规定](http://whhly.shandong.gov.cn/art/2018/10/26/art_70739_6714054.html)〕
> · 〔官方预警〕烟台 — 阵风达 9 级（19.6 m/s），已达【大风黄色预警】发布标准
>   〔[中国气象局](https://www.cma.gov.cn/2011xzt/2022zt/20220330/2022033011/202204/t20220412_4750933.html)〕
>
> **最终是否停航由承运人与主管部门决定，请以官方通知为准。**

每一句都可查、可验证、能点名出处。而且对用户**更有用**——他真正想知道的不是抽象的"高风险"，
是"到底哪条线被越过了、严重到什么程度"。

### 两条 `PROD` 规则的理由

**小船遇海浪蓝色预警 → HIGH**（官方只给了分船型的风速禁航线，没给分船型的浪高线）

> 官方对小船的风速禁航线本就比大船严（6 级 vs 7 级），我们按同样的保守比例响应海浪预警；且涌浪场景（台风远在千里、本地风不大但涌很大）下风速判据会漏判，而那正是小型船艇最容易出事的情况。

**航空 平均风 ≥15 m/s → HIGH**

> 接近常见窄体机干跑道最大侧风分量（B737 约 15 m/s、A320 约 29 节），且我们用总风速近似侧风（没有跑道方位算不出真侧风）。注意：湿滑跑道下该限制会明显更低。

**航空雷暴 → MEDIUM**

> 无对应法规阈值。依据是运营经验：雷雨季民航局的正常率目标为 70%+，强对流下取消与延误风险显著上升。

### 每条来源的已知局限

- **[沿海防大风管理规定（小型船艇禁止出海）](https://www.chinanews.com.cn/sh/2026/08-31/10687414.shtml)** — 原文为「风力预计达到 6 至 8 级时，乡镇船舶、海钓船、休闲船艇、游艇等禁止出海」。属地方/专项管理规定，非全国统一法规，不同海事辖区可能不同。
- **[山东省规定（7 级以上不得允许旅客、车辆上船）](http://whhly.shandong.gov.cn/art/2018/10/26/art_70739_6714054.html)** — 地方规定。渤海海峡客滚船 2018-10-26、2026-02-05 的实际停航与之吻合。其他海区未必执行同一数字。
- **[中国气象局《大风预警信号》](https://www.cma.gov.cn/2011xzt/2022zt/20220330/2022033011/202204/t20220412_4750933.html)** — 全国统一标准。平均风力与阵风取「或」关系，任一达标即发布。
- **[海浪预警分级（近岸海域有效波高）](https://news.cnr.cn/native/gd/20240724/t20240724_526812240.shtml)** — 近岸与近海阈值不同，本工具取港口坐标，适用【近岸】档。另有硬定义：超过 4 米为灾害性海浪。
- **[民航局《航空器机场运行最低标准的制定与实施规定》](http://www.caac.gov.cn/XXGK/XXGK/MHGZ/201511/P020151103350133392047.pdf)** — RVR 低于 400 米称为「低能见度起飞(LVTO)」，需机场 LVP、机组资质、航空器设备三方齐备。这是运行门槛，不是禁飞令。着陆最低标准另计（一类约 550m，二类 300m，三类更低）。
- **[常见窄体机侧风限制（厂商公布值）](https://www.kepuchina.cn/article/articleinfo?business_type=100&classify=0&ar_id=257490)** — B737 干跑道约 15 m/s（30 节）、A320 约 29 节，全机型区间 25–33 节。【湿跑道 B737 降至 12 m/s，刹车效应中等以下降至 7 m/s】。分机型、分道面，不是通用红线。
- **[ICAO 重要气象情报（SIGMET）](https://aviationweather.gov/gfa/#sigmet)** — 由各飞行情报区的气象监视台发布，是航路危险天气（雷暴、积冰、颠簸、火山灰、热带气旋）的官方产品。【有效期只有 4-6 小时】，所以只能用于当天查询，而且我们不知道用户具体几点的航班——文案必须带上有效期让用户自己判断。
- **[《长江干线恶劣天气等条件下船舶禁限航管理规定》](https://xxgk.mot.gov.cn/jigou/aqyzljlglj/202006/t20200623_3316290.html)** — 内河规定，本工具面向沿海，仅作为「船越小限制越严」这一分档方向的旁证，不直接采用其数值。
- **[交通运输部关于十三届全国人大一次会议第 6750 号建议的答复函](https://xxgk.mot.gov.cn/jigou/haishi/202006/t20200630_3319352.html)** — 官方明确：船舶稳性按风压计算，与蒲福风级不对应，故不在船证上标注抗风等级，以免引起社会误解。这是本项目「不预测停航、只陈述越线」的直接依据。

## 证据分层

系统把证据分成两类，边界写死在代码里：

| | **必需证据** | **补充证据** |
|---|---|---|
| 谁去取 | `evidence.py` 确定性预取 | 模型自己决定调不调 |
| 内容 | 两端风速 / 能见度；船舶再加两端有效浪高 | 气象预警搜索、第三地（经停/备降场）天气 |
| 缺了怎么办 | **abstention，明确说"无法判断"** | 无所谓，结论正确性不依赖它 |
| 进不进规则引擎 | 是，规则引擎只看它 | 否 |

**为什么必需证据不交给模型去调工具**：AgentAbstain（[arXiv 2607.10059](https://arxiv.org/abs/2607.10059)，2026-07）
实测最强模型在成对弃权任务上只有 **59.5%** 准确率，且论文发现**弃权能力与通用任务能力基本无关**——
把模型换强并不能解决这个问题。安全关键证据的获取，不能取决于模型这一次想不想调工具。

模型的自由裁量空间仍然是真实的（它可以一次工具都不调直接下结论，也可以主动去查预警和第三地），
只是这份自由不再承担安全责任。

```
POST /api/assess
  ├─ evidence.build_evidence()   确定性预取 ── 港口白名单 → 坐标 → wttr.in + Open-Meteo Marine
  ├─ 证据不足？ → 直接 abstain，跳过模型调用
  ├─ agent.run_agent()           ReAct 循环 ── 模型可调补充证据工具
  ├─ rules.evaluate()            verifier ── abstain / Override UP / Override DOWN
  └─ 返回结论 + evidence + 真实 trace
```

### 真实执行轨迹

结果页可以展开本次请求的**真实**执行记录：每一步的类型（确定性预取 / 模型自主 / 模型 / 规则引擎）、
实际参数、实际耗时、成功还是失败。工具失败会显眼地标红，不会被吞掉。

```
确定性  resolve_location {"name":"上海","require_marine":true}   上海 via whitelist
确定性  get_weather_forecast {"location":"31.36,121.68",...}     wind 9.2 m/s, vis 9.0 km    901ms
确定性  get_marine_forecast  {"lat":31.36,"lon":121.68,...}      wave max 0.42 m             568ms
模型    qwen:qwen-plus                                           输出最终结论               7309ms
规则引擎 rule_engine                                             decision_source=llm → MEDIUM
```

配合 evidence 里每个数值都带的 `source` 与 `fetched_at`，每个结论都能追到**是哪个源、什么时候取的哪个数**。
这正是 TelemetrySuffBench（[arXiv 2608.07899](https://arxiv.org/abs/2608.07899)）说的
"explicit decision-to-provenance links"。

## Abstention：证据不足就不下结论

`risk_level` 有第四种取值 **`UNKNOWN`**。触发时前端显示石板灰的「证据不足」，
**不显示出行建议徽章**（`is_go_recommended` 为 `null`——没有依据就不能落成"不建议出行"），
并列出到底缺了什么、该去查哪个官方渠道。

触发条件（任一命中）：

- 出行日期超出可用预报范围
- 任一端大气数据不可得，或缺必需字段（航空还要求能见度——那是硬红线，缺了就不能排除高风险）
- 船舶出行且任一端拿不到浪高：坐标解析失败、回验判定非海域、或海洋 API 挂了

**判定权在规则引擎，不在模型。** system prompt 里也给了模型一个出口
（Anthropic 评测指南：*"give the LLM a way out, like providing an instruction to return 'Unknown'
when it doesn't have enough information"*），但那只是第二道保险。

这条修的是真实漏洞，不是知识点：改之前，数据缺失时代码默认 `visibility_km=999`、`wind=0`，
也就是**「缺数据 = 安全」**。对一个安全相关产品，这是最坏的默认值。

## 规则引擎 verifier

站在模型循环之外的一层，做三件事：

- **Abstention**：证据不足 → `UNKNOWN`，优先于一切
- **Override UP**：气象数据越过硬红线但 LLM 判低了（包括模型弃权）→ 强制升级
- **Override DOWN**：LLM 判了 `HIGH` 但结构化指标不支持 → 降级。**只对 HIGH 生效**——
  `MEDIUM` 代表 LLM 对多因素边缘组合（如接近阈值的风速叠加雷暴）的综合判断，
  硬阈值捕获不了，应予保留

输出 `decision_source` 字段透出走了哪条路径：`llm` / `rule_override_up` / `rule_override_down` /
`rule_only` / `llm_abstain` / `abstain_insufficient_evidence`。

### 判据结构：两条轴

- **轴 A 禁限航（`REG`）**：官方明文"禁止/不得"的条款。**只有这个配得上"依规不得开航"的措辞。**
  小船 ≥6 级禁止出海；大船 ≥7 级不得允许旅客、车辆上船。航空**没有通用禁飞线**——我们把这一点明说出来，不假装有。
- **轴 B 官方预警（`WARN`）**：气象/海洋部门的四色预警发布标准。只说"已达 X 色预警发布标准"，不预测后果。

完整阈值与出处见上面的[规则来源表](#规则来源表)。三点说明：

- **阈值语义是严格的**：`≥` 表示边界值本身触发，`>` 表示不触发，禁止四舍五入。
  评测里用 10.7/10.8、13.8/13.9、14.9/15.0、2.4/2.5 四组边界值验证精度。
- **大风预警同时看平均风与阵风，取「或」关系**。上一版只用平均风，阵风字段采集了却一直闲置——
  实测烟台→大连航线上，触发预警的常常是阵风而不是平均风。
- **船型只影响禁航线（6 级 vs 7 级），不影响浪高**。因为官方只给了分船型的风速禁航线，
  没给分船型的浪高线。唯一的例外是那条标注为 `PROD` 的小船浪高规则，理由写在来源表里。

### 航路采样：为什么不只看两端

跨海航线的风险由**开阔水域的中段**决定，两端港口是遮蔽水域，会低估。
实测 2026-02-05 渤海海峡全线停航当天：**烟台港平均风只有 8.0 m/s（大风蓝色），
海峡中部却是 15.2 m/s（7 级，已越过客运禁航线）、阵风 21.3 m/s（大风黄色）。**
只采港口会把这次停航判成中风险。

采样点数按距离定（每 ~200 km 一个，上限 5）。但有一个几何限制值得说清楚：
**中国海岸线是弯的，远距离两港之间的大圆直线会切进内陆。** 实测：

| 航线 | 距离 | 采样点落在海上 |
|---|---|---|
| 厦门→金门 | 23 km | 1/1 |
| 烟台→大连 | 154 km | 1/1 |
| 青岛→上海 | 538 km | 2/2 |
| 上海→厦门 | 845 km | **0/4** |
| 天津→北海 | 2117 km | **0/5** |

所以采样点会**自过滤**——取不到浪高的点说明它落在陆地上、不在真实航路上，
丢掉，并把覆盖情况如实透出（`route.on_water`）。长航线大圆穿越陆地时，
结论降级为 `quality: partial` 并明确告诉用户"未覆盖航程中段"，
而不是拿陆地上的地面天气冒充航路气象。

**这个限制在实践中影响很小**：中国沿海的定期客运几乎全是短程横渡
（渤海海峡 154 km、琼州海峡 26 km、厦门-金门 23 km），长途沿海客运
已基本被航空和铁路替代——上海到香港就没有定期客运轮渡。

## 航路：为什么两端不够，以及补到什么程度

用户提的问题：「我们只看出发地和目的地，不看途经点，落脚点是不是站不住？」
查证后答案分两半，而且两半的结论相反。

### 海事：站得住，因为中国沿海客运本来就只有短程横渡

IMO 航行计划准则（A.893(21)）要求对**整个航程**预见不利天气，形式上途经点必须考虑。
但真实做法分两类——中国气象局的资料说得很直白：**"远洋导航有很多航线选择……
而短途航运通常关注更简单的导航需求"**：

- **远洋长航线**：有一整个「气象导航」行业在做**避台**和**绕航**，核心动作是**改航线**，不是停航
- **短程横渡**：整条航线在同一个天气系统里，**没有绕的余地**。决策就是二元的停或不停

而中国沿海的定期客运几乎全是后者——渤海海峡 154 km、琼州海峡 26 km、厦门-金门 23 km。
**长途沿海定期客运已基本被航空和铁路替代**：上海到香港就没有定期客运轮渡，只有邮轮。

所以我们做的[航路多点采样](#航路采样为什么不只看两端)对这个市场是够的。

### 航空：补上 SIGMET，但**没有**为此牺牲覆盖

真实处置顺序是**先绕，绕不过才取消**：

```
航路有雷雨 → ① 申请绕飞 → ② 不批准则返航/备降
           → ③ 大范围覆盖绕不过，或起降机场长时间被覆盖 → 等待或取消
```

民航局的十二类不正常原因统计佐证：2025 年**空管（含流量）原因仅占 0.02%**，
而流量限制正是航路绕飞在运行上的主要体现。**航路天气主要被吸收成延误，很少构成取消的独立原因。**

补的方式是接入 **SIGMET**——航路危险天气的 **ICAO 官方产品**，不是自己编的阈值。
中国各飞行情报区都在发布（严重积冰、嵌入性雷暴、热带气旋），数据带多边形几何，
可判断航路是否穿越。**但只用于当天查询**：SIGMET 有效期只有 4–6 小时，
触发时定 `MEDIUM`（处置是绕飞不是取消），文案带有效期让用户自己判断。

### 一次被回滚的过度收紧（值得记下来）

发现 METAR/TAF 之后，我一度把航空数据源**整体**换成官方机场气象，覆盖从
"任意城市 × 3 天"塌缩到"38 个机场 × 30 小时"。理由听起来很正当——"安全工具不该跑在非官方数据上"。

**这个判断是错的**，两个原因：

**① 我把"跑在错的数据上"说过头了。** 拆开看三条航空判据：

| 判据 | 城市地面天气够不够用 |
|---|---|
| 大风预警（平均风/阵风四色） | **完全够用**——大风预警本来就是**对区域**发布的，城市地面风正是它的输入 |
| LVTO 能见度（RVR < 400m） | 真的是近似——城市能见度 ≠ 跑道 RVR |
| 侧风 15 m/s | 本来就是分机型分道面的近似，已标 `PROD` |

三条里只有一条真的因此改善，却为它砍掉了 90% 的覆盖。

**② 原则被用得不一致。** 项目的规矩是「知识库里只放有官方出处的**阈值**」——
那是关于阈值的，不是关于数据源的。海事一直用 Open-Meteo Marine（数值模式，非官方预报产品）、
用 wttr.in、L4 用 ERA5，都标注来源就接受了。偏偏对航空套一条更严的"只用官方产品"，是双标。

**而且对一个决策工具来说，覆盖率本身就是产品质量。**
一个大多数查询都回答"证据不足"的安全工具，不会让任何人更安全，只会让人不用它。

**现在的做法**：官方优先，取不到就回落，并在证据里标明用的是哪一种。

| 情况 | 数据源 | 证据里的标记 |
|---|---|---|
| 38 个机场 + TAF 覆盖范围内 | 官方 METAR/TAF | `aviationweather-taf` / `quality: full` |
| 其余机场，或超出 TAF 范围 | 城市地面天气 | `wttr.in` / `quality: city_surface` |

前端会在结果里明确提示哪次用了城市地面天气。这比"要么官方要么弃权"更诚实，
也更有用——**该说清楚的是数据的出处和局限，不是把用户挡在门外。**

## 可达性契约：两条路径都要能拦住"前提不成立"的查询

用户实测发现的一个真漏洞，值得单独写出来。

**船舶侧因为需要浪高，顺带获得了一个校验**：Open-Meteo Marine 对内陆点返回全 null，
所以"内陆当船走"会被自动拦下。**航空侧没有这个天然校验**——航空判据只要风速和能见度，
而**任何地名都能查到风速和能见度**。结果：

```
上海 → 南极      飞机  →  低风险，建议出行   ← 修复前
北京 → 珠穆朗玛峰 飞机  →  正常出结论        ← 修复前
舟山 → 嵊泗      飞机  →  低风险            ← 嵊泗没有机场
```

这和整个项目一直在修的是同一类错误：**回答一个前提不成立的问题**。
跟"缺数据默认安全"、"编一个没出处的阈值"是一个家族的。

修法和港口白名单同构：加一份**民航机场白名单**（149 个），清单外一律弃权。
清单刻意不追求完整——**漏收一个支线机场会导致弃权（安全方向），
错误放行一个不存在的航点会导致"建议出行"（危险方向）**，两种错误的代价不对称。

同时把弃权文案分成了两类，因为它们对用户是完全不同的信息：

| 情况 | 修复前 | 修复后 |
|---|---|---|
| 上海→拉萨（船） | "地点无法解析为可用的海域坐标"（像系统坏了） | "该地点不临海" |
| 杭州→南京（船） | 同上 | "不临海。**内河与湖泊航线不在覆盖范围内**——内河另有一套官方标准，判据是风力分档且不含浪高" |
| 上海→南极（飞机） | 低风险，建议出行 | "该地点不在已收录的民航机场清单内" |

L3 里有一组专门钉死这两个漏洞的断言，L2 里有对应的端到端场景。

## 四层评测

```bash
python -m evals.l3_sufficiency    # 确定性断言，零 token   ← 改动后先跑这个
python -m evals.l2_integration    # 真实网络 + 真实模型
python -m evals.l4_realworld      # 真实停航记录回验，零 LLM
python -m evals.l1_reasoning      # 39 条用例 × N 个模型横评
python -m evals.run_all           # L3 → L2 → L4 串跑；--with-l1 带上横评
```

| 层 | 测什么 | 隔离掉什么 | 代价 |
|---|---|---|---|
| **L1 推理层** | 给定数据下 LLM 的判断质量 | 网络、数据源、真实世界波动 | 花 token，几分钟 |
| **L2 集成层** | 端到端结论是否成立、自洽 | 无（就是要真实） | 花 token + 网络，~60s |
| **L3 数据充分性层** | 该有的数据到底拿到没有 | LLM 完全不参与 | 零 token，~20s |
| **L4 真实世界回验** | **阈值跟现实中真的停不停航对不对得上** | LLM 完全不参与 | 零 token，~40s |

**为什么不能互相替代**：L1 可以 100% 而 L3 是 0%；L1/L2/L3 全绿而 L4 告诉你阈值本身有系统性缺口。
这两件事都不是假设——都在这个项目里真实发生过。

- **L1**（39 条标注用例，工具全 mock）：模型横评、边界精度、规则引擎增益。
  灰色地带用例标 `acceptable` 多值，避免把 prompt 的固有模糊性误计为模型错误。
  含 6 条弃权用例、4 组边界值三连测、3 组船型对照，分别统计「规则门是否正确弃权」与「模型自己是否提出 UNKNOWN」。
- **L2**（真实工具调用）：断言全是**不变量**而非固定风险等级——真实天气每天在变，
  把等级钉死必然天天红。包括：schema 合法、证据带 `source`/`fetched_at`、
  **拿返回的 evidence 重跑规则引擎结论必须自洽**、内陆当船走必须弃权、
  日期超范围必须弃权、**故障注入**（把海洋 API 指向不可达主机）后必须弃权而不是静默给低风险。
- **L3**（确定性断言，不调 LLM、不需要 API Key）：白名单每个港口都能取到浪高、
  内陆对照点必须取不到（确认判别器有判别力）、风速/阵风/能见度可得且能按日期精确对齐。
- **L4**（真实世界回验，不调 LLM）：拿 25 条**已公布的停航/通航记录**，用 ERA5 历史存档
  重建当天的风浪，跑规则引擎，算召回率和误报率。**标签不需要专家判断——
  "那天实际停没停航"是官方与媒体已公布的客观事实。**

三层都遵守 Anthropic 评测指南的一条警告：**不评工具调用顺序**——
原文说这种做法*"too rigid and results in overly brittle tests, as agents regularly find
valid approaches that eval designers didn't anticipate"*，要 grade what the agent produced,
not the path it took。L3 测的是「拿到数据没有」这个能力，不是「按什么顺序调」。

## 评测结果

### L4 真实世界回验：把阈值放到真实停航记录上验

25 条已公布的停航/通航记录（琼州海峡 + 渤海海峡，2025–2026），用 ERA5 历史存档
重建当天风浪，跑规则引擎：

| 指标 | 结果 |
|---|---|
| **误报率**（正常通航日 → 判 HIGH） | **0/10 = 0.0%** |
| 过度预警率（正常通航日 → 判 HIGH 或 MEDIUM） | 1/10 = 10.0% |
| 逐日召回率（停航日 → 判 HIGH） | 4/13 = 30.8% |
| 预警覆盖率（停航日 → 判 HIGH 或 MEDIUM） | 10/13 = 76.9% |
| **事件级召回率**（一次停航窗口内任一天判 HIGH） | **4/7 = 57.1%** |

**误报率 0% 是好消息**：我们从没在服务正常运行的日子里喊过狼来了。
**召回率低才是这一层的价值**——它逼出了两个我自己想不到的结论：

**① 我们缺了一整条轴：台风预警。** 9 条漏判里有 7 条是台风相关。
承运人依据**台风预警**提前停运，而台风预警是独立于风力/浪高的另一套官方信号，
我们完全没有建模。实测台风「风神」整个停运窗口内风速 10.1–13.4 m/s，
始终落在我们的 MEDIUM 档——**不是阈值定错，是缺了一条轴**。
这个缺口我选择**记录下来而不是补一个拍脑袋的阈值**，因为补的那个阈值又会变成新的无来源经验值。

**② 剩下 4 条是"贴线漏判"**：平均风 12.0–13.9 m/s，就差在大船禁航线（13.9）下方。
ERA5 网格约 0.25°，在海峡这种地形复杂处会平滑掉局地峰值风——新闻报道的实际风力
（如"8–10 级"）普遍高于重建值。

**方法论限制（必须一起读）**：ERA5 是**再分析**，事后用观测重建的"实际发生了什么"，
不是决策当时可得的**预报**。所以这一层验证的是「**阈值与实际停航是否吻合**」，
不是「当时的预报能否预测停航」。这两件事经常被混为一谈。

**能力边界（单独列出，不计入指标）**：2 条停航的原因是南海开渔和船舶检修——
非气象原因，我们判不了也不该判。把它们留在数据集里，是为了证明我们知道自己管不了什么。

> 数据集：[`evals/golden/events.jsonl`](evals/golden/events.jsonl)，每条带来源链接与原文摘录。
> 事件由网络检索收集，建议抽查。

### L1 推理层（39 条标注用例，工具全 mock，2026-09-01）

| 模型 | LLM 裸判 | 安全网后 | 提升 | 主动弃权率 | JSON 合规 | 平均耗时 |
|---|---|---|---|---|---|---|
| **deepseek-v4-pro** ✓ 生产 | **89.7%** | **100%** | +10.3pp | 33.3% | 100% | 27.5s |
| kimi-k3 | 87.2% | **100%** | +12.8pp | 16.7% | 100% | 50.4s |
| glm-5 | 71.8% | **100%** | +28.2pp | 0.0% | 87.2% | 26.4s |
| qwen-plus | 56.4% | **100%** | +43.6pp | 0.0% | 100% | 6.9s |

**四家模型全部 100%，安全网后零残留错误。**

> 复现：`python -m evals.l1_reasoning`（用例并发，约 5–8 分钟）。单次运行结果，
> 模型在边界用例上有一定随机性——qwen 复跑一次是 61.5%，量级不变。

### 换成官方判据之后，模型裸判反而更难了

对比上一版（旧阈值）：qwen 71.1%→56.4%、glm 71.1%→71.8%、kimi 89.5%→87.2%、
deepseek 92.1%→89.7%。**裸判普遍下降，而安全网后从 97.4–100% 升到全部 100%。**

原因不是模型变差，是规则变细了：四色预警分档、平均风与阵风取「或」、
船型分档的禁航线、两条标注为 `PROD` 的例外。**判据越细，模型越容易在某一档上滑一格，
而确定性 verifier 的价值也就越大。**

### 最值得注意的一个数字：弃权漏判率 87.5%

6 条证据有洞的用例（浪高拿不到、能见度拿不到、日期超范围、数据源挂掉……），
system prompt 明确写了「宁可说不知道，不要猜」，证据 JSON 里那些字段明明白白是 `null`。
四家模型合计 24 次弃权机会，**错过 21 次（87.5%），而且 21 次全部判 `LOW`**。

| | qwen-plus | glm-5 | kimi-k3 | deepseek-v4-pro |
|---|---|---|---|---|
| 主动弃权率 | 0/6 | 0/6 | 1/6 | 2/6 |

更说明问题的是**错误的分布**：deepseek 全部 4 条错误、kimi 全部 5 条错误，
**无一例外都是弃权用例**——在有数据的 33 条上它们一条不错。
也就是说这两个模型判断力没问题，**唯独在"数据缺了"这件事上集体失灵，一致地读成"一切正常"**。

这正是改造前那版代码的行为（缺数据时默认 `visibility_km=999`、`wind=0`），
也在本地复现了 [AgentAbstain](https://arxiv.org/abs/2607.10059) 的核心结论：
**弃权能力与通用任务能力基本无关。**

这 24 次最终全部正确，因为**弃权判定压根没交给模型**。

### 安全网的第二种救场：模型输出完全不可用时

glm-5 有 5 条用例输出了无法解析的 JSON（合规率 87.2%）。这种情况下 `llm_output` 为 `None`，
规则引擎走 `rule_only` 路径独立出结论——**5 条全部正确**。

同样的路径在真实故障下也验证过：L2 的故障注入把所有 LLM key 换成无效值，
系统照样返回合法结论，`decision_source=rule_only`，模型调用失败如实进 trace 不被吞掉。

### 历史结果（仅供对照，三版用例集互不可比）

| 版本 | 用例数 | 变化 |
|---|---|---|
| V1.6 | 30 条 | 浪高是从天气描述文本里正则抠的中文串（生产环境恒为 None） |
| V2.0 | 38 条 | 浪高改为结构化字段，新增船型对照与弃权用例 |
| V3.0（当前） | 39 条 | 阈值全部换成有官方出处的，新增阵风与 `PROD` 规则用例 |

V1.6 的 deepseek-v3 96.7%、hunyuan +13.3pp 那组数字是真的，但**它们验证的是规则引擎的逻辑，
不是数据管线，更不是阈值本身对不对**——两条教训见下一节。

## 两条评测设计教训

### 教训一：评测隔离得越干净，越容易漏掉集成层的问题

第一版最值得写下来的一条：

> 我的评测把工具调用全 mock 掉，为的是隔离推理能力——代价是把数据管线的洞藏了起来。
> **评测隔离得越干净，越容易漏掉集成层的问题。** 所以改成了三层评测。

具体发生了什么：上一版的海事浪高判定，是用正则 `(?:有效浪高|浪高)\s*([\d.]+)\s*米`
**从天气描述文本里抠中文**。而气象数据源（wttr.in）压根不返回任何海洋字段——
所以浪高在生产环境恒为 `None`，两条浪高规则从不触发，船舶的 Override DOWN 也永远不生效。

为什么半年没被发现：mock 数据里写死了 `description="大浪，有效浪高 3.0 米，涌浪发展"`，
正好喂给那个正则。于是 20 条涉浪用例全过。**96.7% 那个数字是真的，
但它验证的是规则引擎的逻辑，不是数据管线。**

这一版把浪高换成了结构化字段（Open-Meteo Marine API 的 `wave_height`），
那条作弊路径连存在的可能都没有了；同时新增的 L3 层会在 20 秒内、
不花一分钱 token 地把这类洞暴露出来。

这条呼应 Anthropic 评测指南的核心主张——没有任何单一评测层能抓住所有问题，
要把自动评测、生产监控、A/B 和人工审查组合起来用（原文用了瑞士奶酪模型作类比）。

### 教训二：知识库也要被评测，而不只是被引用

第一轮我把注意力全放在"数据管线通不通、评测分不分层"上，默认了一件事：
**system prompt 里那些阈值是对的。**

它们不对。逐条查证后：8 条里 1 条错在危险方向（大船 17.2 应为约 13.9，我们放宽了）、
1 条查不到任何来源（浪高 1.5m 中风险）、3 条数字有出处但我们的措辞夸大了它的含义。
更尴尬的是，我在文档里一直写"规则来源只给了分船型的风速红线"——那个"来源"
其实是这个项目自己的 PRD，等于**自己引用自己**。

> 数据管线可以被评测抓到，因为它有"取到 / 取不到"这种客观状态。
> 而知识库的错误是**静默的**：阈值写错一个数字，所有测试照样全绿，
> 因为测试的期望值就是照着那个错阈值标的。

所以这一轮做了三件事：**(1)** 阈值和出处集中到
[`rules_sources.py`](rules_sources.py) 单一事实来源，README 的表由它生成，杜绝漂移；
**(2)** 每条判据强制标注来源类型（法规 / 官方预警 / 本工具判定），
无出处的一律删除；**(3)** 新增 L4，用**真实世界的结果**回验阈值——
这是唯一能发现"阈值本身错了"的评测层。

## 范围决策：明确不做什么

| 不做 | 理由 |
|---|---|
| **memory / 上下文压缩 / compaction** | 这是单轮决策查询：用户填表 → 拿一个结论。天然没有长程任务，没有需要跨轮记住的状态。加进来只是堆名词 |
| **multi-agent / subagent** | 任务是「取两三处数据 → 比对阈值 → 出结论」。拆成多个 agent 只增加协调开销和失败面 |
| **RAG** | 规则总量不到 300 字，塞进 system prompt 秒级生效。这个体量上向量检索是负收益 |
| **补一个台风阈值** | L4 显示台风相关漏判 7 条，但补一个拍脑袋的阈值就是在重犯这一轮刚修掉的错。缺口记录下来，等有官方台风预警数据源再说 |
| **SSE 流式轨迹** | 演示观感更好，但 Vercel serverless 上要多一层适配、代理缓冲可能让线上 demo 卡住。收益不值这个线上翻车风险，改为响应到达后渲染真实轨迹 |

判断「什么该用 AI 做、什么不该」本身就是这个项目要展示的能力之一。

## 已知取舍

写在这里而不是偷偷藏着。**这一节是这个项目最该被读的部分。**

### 能力边界（我们判不了的）

- **台风预警没有建模** —— L4 实测：9 条漏判里 7 条是台风相关。承运人依据台风预警提前停运，
  那是独立于风力/浪高的另一套官方信号。**我选择记录这个缺口，而不是补一个拍脑袋的阈值**，
  因为补出来的又是一个无来源经验值
- **非气象原因的停航** —— 渔汛、船舶检修、军事管制。数据集里刻意留了 2 条这类样本
- **内河与湖泊航线不覆盖** —— 内河另有一套官方标准
  （[《长江干线恶劣天气等条件下船舶禁限航管理规定》](https://xxgk.mot.gov.cn/jigou/aqyzljlglj/202006/t20200623_3316290.html)：
  游览船/渡船 5 级、滚装船及 ≤80m 船 6 级、其他内河船 7 级禁航），**判据是风力分档且完全不含浪高**，
  与本工具采用的海事判据不通用。杭州→南京这类河运航线会明确弃权并说明原因
- **不核实航线是否存在** —— 我们只校验两端各自是不是真实的港口/机场，
  不校验"这两地之间真的有航班/航线"。后者需要航线数据库
- **航空分两份清单** —— 可达性清单（149 个有机场的城市，决定"能不能评估"）与
  官方气象清单（38 个发布 METAR/TAF 的机场，决定"用哪个数据源"）。前者不完整，
  漏收会导致弃权（安全方向）；后者按**实测发报**定而不是按站点库标称
  （拉萨等 20 个标称有数据但实际没发报）
- **能见度在回落时是近似值** —— 城市地面能见度不等于跑道 RVR。证据里标了 `city_surface`，前端会提示
- **TAF 只覆盖约 30 小时，查"明天"时通常只覆盖 20/24 小时** —— 未覆盖的时段用城市地面天气补齐，
  取合并后的极值（`quality: mixed`），并在结果里写出**官方预报覆盖到几点**，
  让用户拿它对自己的航班时间。不补齐会漏掉晚间大风，那是"该警告时不警告"方向的错
- **"能不能通海"判的是城市不是像素** —— 之前只测 geocoding 给的市中心坐标在不在海洋网格里，
  杭州（杭州湾湾顶）因此被误判为内陆。现在在 **50 km** 半径内搜最近的海域网格。
  半径是实测定的：可通海城市（杭州/嘉兴/台州）最近海域都在 50 km 内，
  内陆城市（南京/镇江/武汉/郑州，含长江沿线）都在 100 km 外
- **SIGMET 只用于当天** —— 有效期 4–6 小时，且我们不知道用户具体几点的航班
- **预报范围只有 3 天** —— wttr.in 只给 today / +1 / +2，超出范围走 abstention 而不是外推
- **航空没有通用禁飞线** —— 我们明说这一点，不假装有

### 判据本身的局限

- **两条 `PROD` 规则不是法规** —— 小船遇海浪蓝色预警、航空 15 m/s 侧风近似。
  在[规则来源表](#规则来源表)里单独标出并附理由
- **地方规定不统一** —— 引用的山东、长江干线等是地方/流域规定，不是全国统一标准，
  不同海事辖区可能不同
- **侧风用总风速近似** —— 没有跑道方位算不出真侧风。且厂商侧风限制是**干跑道**值，
  湿滑跑道下会明显更低
- **浪高不分船型** —— 官方只给了分船型的风速禁航线。唯一例外是那条标注为 `PROD` 的规则
- **官方气象清单按实测可得性定** —— 38 个，从官方站点接口导出并逐个探活
- **海事覆盖 = 港口白名单（80 个）** —— Open-Meteo Geocoding 对中国地级市覆盖很差
  （population 字段全为 null，返回同名村镇：阳江→江苏、营口→黑龙江，泉州返回 0 条），
  兜底基本失效。所以白名单必须扩够，每条都经 L3 验证能取到浪高


### 评测方法的局限

- **断言不能依赖当前时刻** —— 曾把"后天一定没有官方预报"写进 L3。但 TAF 有效期约 30 小时、
  覆盖窗口随签发时刻整天滚动，傍晚签发的 TAF 尾巴会伸进"后天"。真正的不变量是
  **覆盖时长与质量标记必须一致**，与当前时刻无关。同样的原因，日期按钮上的静态
  "今天=官方/后天=城市天气"标注也被移除了——它在一天中的某些时刻必然是反的
- **ERA5 是再分析不是预报** —— L4 说明的是"阈值对不对"，不是"预报够不够用"
- **ERA5 网格 0.25°** —— 海峡等地形复杂处会平滑掉局地峰值风，导致召回率偏低
- **黄金集事件由网络检索收集** —— 来源链接与原文摘录全部留档，需要人工抽查。
  16/25 条的日期是从"预计持续至 X"或复航公告**推断**的，已在数据里标注 `confidence`
- **海洋历史存档约从 2021 年起** —— 更早的事件取不到浪高，已从数据集剔除

### 工程上的取舍

- **航线中点是 best-effort** —— 取不到不触发 abstention（两端的必需证据已经齐了），
  只在 trace 里如实记录
- **端到端延迟 ~10–30s，主要是模型** —— 实测：证据预取 2.1s（6 次网络调用已并发化），
  deepseek-v4-pro 单次约 27s。Vercel 函数硬上限 60s，所以模型调用设了 **32s 超时并降级到
  `rule_only`** ——那条路径本来就存在且验证过，比让用户吃 504 好得多。
  试过 `deepseek-v4-flash`（21.7s）但裸判掉到 74.4%，不划算
- **限流是 best-effort** —— 内存实现，serverless 上按实例隔离。真正的限流需要外部存储，超出范围
- **预警搜索可能在云端失效** —— DDGS 从数据中心 IP 大概率被限流。它是**补充证据**
  （不进 abstention 门），失败不影响结论，只会在 trace 里显示为失败
- **Vercel 自动部署未接通** —— 每次改动需手动跑 `./deploy-vercel.sh`

## 自己验证

不用信 README 里的数字，两条命令就能自己跑：

```bash
python -m evals.l3_sufficiency
```
**~30 秒，零 token，不需要任何 API Key。** 179 条确定性断言：80 个港口能否取到浪高、
内陆对照点是否被正确排除、航路采样是否落在海上、机场清单可达性、TAF 覆盖与补齐、
边界城市判定。改动之后的第一道检查就是它。

```bash
python -m evals.run_all
```
L3 → L2（真实网络 + 真实模型，含 3 组故障注入）→ L4（真实停航记录回验）。

线上也可以直接点，几个值得试的：

| 输入 | 会看到什么 |
|---|---|
| `烟台 → 大连` 船只 | 证据里有**航线中点**——只采港口会漏判真实停航 |
| `上海 → 广州` 飞机 | **官方机场预报覆盖至 X 时**；有时能看到 **SIGMET** 航路情报 |
| `北京 → 西安` **船只** | **证据不足**，且**不显示出行建议**——这是本项目的核心主张 |
| `上海 → 南极` 飞机 | 弃权，而不是"低风险，建议出行" |
| 展开 **Agent 执行轨迹** | 真实工具名、参数、耗时；确定性预取与模型自主调用分开标 |

## 快速启动

```bash
pip install -r requirements.txt
echo "DASHSCOPE_API_KEY=your_key_here" > .env
uvicorn app:app --reload
```

打开 http://localhost:8000

支持四家模型，`VOYAGEGUARD_PROVIDER` 切换（`qwen` / `deepseek` / `kimi` / `glm`），
每家的 model id 可用 `VOYAGEGUARD_MODEL_<PROVIDER>` 覆盖，都不用改代码。

### 部署

Vercel 的 Python framework preset 自动识别项目根 `app.py` 里的顶层 `app` 作为 ASGI 入口，
不需要 `api/` 目录。推 GitHub 即自动部署，环境变量配在 Vercel 项目设置里。

`Dockerfile` 保留给自托管场景（端口 7860）。
